notes:
- render= is the time of mpv_render_context_render per frame. It includes mpv's wait for the target time (BLOCK_FOR_TARGET_TIME default 1, vo_libmpv.c:425-431), so it is an upper bound on render work and sits close to the frame period (16.67 ms at 60 fps) when the work finishes early. A max_render far above 16.7 ms marks a stall inside the render call.
- describe= covers Describe's entry through AcquireFront.
- A handle_change_ratio near 1 means Flutter's one-handle cache misses on nearly every frame (the descriptor carries a different DXGI shared handle than the previous one).
- bind= is Describe's return to the release callback: the GL bind plus, on a handle change, eglReleaseTexImage, eglDestroySurface, eglCreatePbufferFromClientBuffer and eglBindTexImage (external_texture_d3d.cc:54-115, Flutter 3.47.8). It excludes the compositor's draw and ANGLE's internal synchronization, which the plugin still cannot time.
- Effective drops = mpv frame-drop-count + superseded. The run lines report drops as the last stats value minus the 10th, which goes negative when the counter resets at a loop seek (drops=-6 and drops=-8 above: 6 and 8 startup drops, all before the 10th stats line, then the counter reset to 0 at the first loop wrap). The table column eff_post10 is the sum of positive counter increments from the 11th stats line on plus superseded (superseded=0 everywhere); drops_raw repeats the run-line value. dec_drops is computed the same way (increments after the 10th stats line).
- Sample deviation: no 3840x2160 59.94 fps H.264 file exists on this host and the user placed none in build\umq\sample\ (checked, directory absent), so the fallback Desktop\1145142.mp4 was used: avc1 3840x2160 at 60.000 fps (not 59.94), 36.9 s, looped (MPV_KIT_EXAMPLE_LOOP=1), so each 135 s run holds about three loop seeks. The numbers are therefore not directly comparable with a 59.94 fps no-loop GTX 960M run.
- The window was the default 1280x720, untouched. Display refresh 165 Hz (Win32_VideoController CurrentRefreshRate).
- No clock locking was used; clocks are as the driver chose them (see the smi lines: the GPU sat mostly in P4/P5 at 750-870 MHz median, load is light). nvidia-smi was only ever called with --query-gpu reads.
- fg_start and fg_end were mpv_kit_example in all four runs (the harness's AppActivate at +10 s was not needed); standby=none and forensics=none for all four; AC power, saver off, hands-off.
