<objective>
VER-01 与 Phase 17 的开局：一个汇总的决策检查点（推送授权与三项口径），然后用 fake 后端故障注入把「回退链 + 带原因的事件」钉成 golden，并按决定处理 macOS 上 vk-gpu-timeout 的计时 flake。

**为什么要先问 VER-01 的口径（Task 1）。** ROADMAP 成功标准 1 写的是「device lost、超时风暴、目标分配失败时渲染切到 auto 链的下一候选」。现在的引擎只在创建时（`VideoRenderer::Start`）走链；控制器启动后，device lost 停止渲染并发一个事件，超时与分配失败按 100 ms→5 s 退避无限重试。在运行中的控制器里换后端需要：释放 render context（render.h：每个 mpv core 同时只能有一个，VO 在用时释放会禁用视频，需要从非渲染线程重新选择 vid）、GPU→software 时更换 Flutter 纹理类型（`textureId` 是 final）、改变 final 的 `backend`/`reason`——这是公共 API 语义的变化，与 RBE-F1（device lost 后原地重建，已列为 Future）相邻，单独成阶段。推荐口径 `create-chain`：故障在创建阶段推进链；运行期故障在当前后端上以带原因的事件进入确定状态；重建时故障仍在则走到下一候选；分配失败与超时风暴不推进链这一边界被 golden 钉住并如实写入 SC1 措辞建议（阶段末交用户批准，执行者不改 ROADMAP）。

**规划时发现的缺陷（17-02 修复，不受 ver01 影响）。** `MpvVideoController.create` 在返回之前向异步广播流 add `softwareFallback`，此时不可能有监听者，事件总是丢失——「落到 software 时发出事件」从未成立。

**flake。** `video_renderer_golden_vk` 的 vk-gpu-timeout 在 hosted macos-15 上测到 retry-ms 1396（期望 1100，窗口 [1095, 1350]，run 40679129407，重跑通过）。该间隔把 VulkanContext 的 1 s 设备等待（驱动/VM 决定）与引擎的首次退避（100 ms）混在一起判定。1 s 超时本身已由 Phase 12 constants_audit 钉住（`1'000'000'000ull`）。measure-split 分两段各自按它所证明的事判定，不削弱：退避上界不再被设备等待的噪声吃掉；设备等待保留下界（超时被遵守）与能区分「1 s」与「2 s 及以上」的上界。
