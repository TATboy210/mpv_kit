<objective>
Phase 15 的构建前置与第一条示踪：让 Linux 的 libmpv 带上上游 OpenGL render API，并用一个新的原生冒烟测试在 ubuntu runner（EGL surfaceless + Mesa llvmpipe）上证明 `MPV_RENDER_API_TYPE_OPENGL` 真的能渲染出非黑像素。构建计划先于任何渲染计划（ROADMAP「构建计划必须先于渲染计划」的同一原则）。

两个前置检查点：
1. **推送与 dispatch 授权（Task 1）。** Phase 12 的 `evidence/push-authorization.txt` 只覆盖 Phase 12。本机是 Windows（MINGW64，无 meson），Linux 只能经 CI 往返证明；GLX-01 的打包、allowlist 与 ABI 审计只在 release.yml 中运行，它只由 v* tag 或 workflow_dispatch 触发。本阶段沿用 Phase 12 的 push-green-only 与「RED 证据只在本地」规则。
2. **Bundle 组成（Task 2，one-way）。** `-Degl=enabled` 让 mpv 的 meson 依赖 `dependency('egl')`（native/mpv/meson.build:1274-1278），打包后的 `libmpv.so.2` 会对宿主的 `libEGL.so.1`（libglvnd）有 DT_NEEDED。package.sh 的系统 allowlist 已包含 `libEGL`，所以它不会被打进 bundle；但这意味着只用 Dart（不用 Flutter）的消费者也必须在宿主上有 libEGL.so.1 才能加载 libmpv。一旦发布，回退就是破坏已发布的宿主要求，所以先问。

**现有 CI 的相关观察（规划时读取，run 40442377807，sha 025bdad）：** native-verify 的 linux job 已安装 libegl-dev libgl-dev，而 `MESON_ARGS` 没有关闭 GL，验证层 libmpv 很可能已经带 GL；但这只是默认值碰巧成立。本计划把它变成显式选项加 config.h 断言，这样 CI 验证的就是发布物要带的东西。

**Flagged assumptions（spec-less edge probe）：** 本阶段没有 SPEC。确定性 edge probe 对 GLX-01 与 GLX-02 返回 `unclassified / unresolved`。本计划只证明 llvmpipe（软件 GL）上的行为；NVIDIA/AMD/Intel 真驱动上的 GL render API 行为在本阶段无法证明，保持「未验证」，不得用 backstop 自动标为已覆盖。两条假设原样写入 SUMMARY。

Purpose: 15-02（原生交接 spike）、15-05（OpenGLBackend）依赖验证层 libmpv 带 GL render API，并依赖 render_gl_smoke 作为载体。
Output: 授权与决策记录、Linux 构建选项与断言、验证层与发布层 workflow 的依赖、`render_gl_smoke`（gl/gles 两个变体）、本阶段的 CI 门脚本副本。
</objective>
