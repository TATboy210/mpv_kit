<objective>
可移植的引擎接缝与 Linux 链数据，全部可以在本机（Windows，MSVC）和每个 CI runner 上运行，不依赖 Linux：

1. **Linux 候选链（GLX-04）是 one-way 决策。** auto 链中 opengl/gpu 排在 vulkan/gpu 之前，意味着 Vulkan gpu-next 不可用的 Linux 用户会落到 OpenGL，而 OpenGL 路径只能在 llvmpipe 上证明，真驱动「未验证」。ADR 0004 Decision 5 定了「渲染器质量优先、API 其次」的原则，GLX-04 定了 auto 的顺序，但 gpu 请求的 API 顺序、以及在真驱动未验证时是否落地，没有任何记录让你选过。所以先问（Task 1），再把数据写进可移植头文件，并用 golden 测试锁住（Task 2）。接入插件在 15-05。
2. **create 期调用的绑定点（GLX-03 / SC3）。** render.h 规定 OpenGL 后端的**每个** `mpv_render_*` 调用都必须在 mpv 的 GL context 为当前的线程上。Phase 12 之后，Start 之后的所有调用已经在渲染线程上（12-11），但 create 期的 `render_context_create`、`get_info` 与第一次 `set_update_callback` 仍在 Start 的调用者（平台线程）上，而且没有任何绑定点。15-03 的规划发现表明 Linux 平台线程上 make current 并不可靠（第二个控制器起探针失败）。所以引入一个最小的接缝 `RenderBackend::RunBound(fn)`：默认实现就在调用者线程上 BindThread → fn → UnbindThread（Vulkan/软件不变）；OpenGL 后端在 15-05 里用它在一个自己的线程上、带 context 执行 create 期调用。

**对 SC3 措辞的解释（在 Task 1 检查点由你决定，不留到阶段末）：** SC3 写「所有 `mpv_render_*` 调用都在渲染线程且 mpv 的 context 为当前」。本计划的设计沿用 Phase 12 已确立的契约（affinity 测试与 video_renderer.h 的文档）：Start 之后的所有调用都在渲染线程上；create 期调用（`Create`、`RendererName`、第一次 `set_update_callback`，以及渲染线程从未运行时析构里的释放）在 `RunBound` 指定的线程上，且 mpv 的 context 为当前。若要求 create 期调用也在渲染线程上，需要让渲染线程先于候选循环启动，这会改变 Vulkan/软件路径已冻结的调用线程（affinity 测试断言 create 在 Start 的调用者上），是另一种引擎设计。Task 1 同时问这个问题；答复记录在 decisions.txt，Task 3 与 15-05 以它为前置条件。执行者不修改 ROADMAP 的 SC3 原文；若你选择 RunBound 解释，15-07 只提出一条措辞更新建议供你批准。

**RED 证据只在本地。** bind 测试先于引擎改动写好并在本地失败，失败日志落盘；RED 提交不单独推送，CI 只看到最终状态（Phase 12 的 push-green-only 规则）。

Output: 链决策、`linux_candidates.h`、两个新的可移植测试与 golden、`RunBound` 接缝。
