<objective>
HWD-03 的宿主侧：Linux 宿主为每个控制器解析与渲染 GPU 匹配的 DRM render node，把它作为 `MPV_RENDER_PARAM_DRM_DISPLAY_V2` 传给 mpv（GL 与 Vulkan 两个后端），并管理 fd 的生命周期。

研究 3.1/3.5 的结论：mpv 只读结构体的 `render_fd`（hwdec_vaapi.c 63-70 行），libmpv 复制结构体但不 dup fd，所以宿主必须在 `mpv_render_context_free` 之后才关闭 fd；x11/wayland 在 bundle 中关闭，DRM 是唯一的 VA 显示来源；render node 名字不可靠（renderD128 不一定是目标 GPU），必须从设备反查。

设计（Claude 裁量，研究 Architectural Responsibility Map 与 Claude's Discretion）：
- 共享的 `src/drm_render_node.h`（header-only，模仿 `linux_candidates.h`）：可移植的结构体填充与路径白名单，以及只在 Linux 编译的「按设备号找 renderD* 字符设备」与「白名单校验后 O_RDWR|O_CLOEXEC 打开」。
- Vulkan 路径：`VulkanInterop` 新增两个带默认实现的钩子（Windows/macOS 不受影响）；`VulkanRenderBackend` 在设备就绪后解析一次、每次 create 带参数、析构时关闭；Linux 的 `GlInterop` 用所选物理设备的 `VkPhysicalDeviceDrmPropertiesEXT` 实现钩子（项目已把 `VK_EXT_physical_device_drm` 列为可选设备扩展，vulkan_backend.cc 47 行；物理设备已按 Flutter GL 设备 UUID 选定，gl_interop.cc AcceptDevice，所以它就是渲染 GPU）。
- OpenGL 路径：`OpenGLBackend` 从 Flutter 的 EGLDisplay 经 `EGL_EXT_device_query` + `EGL_EXT_device_drm_render_node`（`EGL_DRM_RENDER_NODE_FILE_EXT` 0x3377）取路径；不可用时不传参数。研究 3.5 的第二回退（GL 设备 UUID → Vulkan 物理设备 → DRM 属性）不实现：它要在 GL 后端里再建 Vulkan 实例，换来的只是缺少 EGL 扩展的驱动（多为 NVIDIA 专有驱动，其 vaapi 本就依赖第三方 nvidia-vaapi-driver）也能尝试 vaapi；该限制写进 unverified.txt。
- 研究 3.5 建议的「GL 与 Vulkan 两种解析互相校验并把不一致写进 reason」不实现：hosted 上两者都返回「无」，校验无法被观测；改 reason 内容又触及 ADR 0004 的语法。两条路径指向同一块 GPU 的依据是 AcceptDevice 的 UUID 匹配，真实硬件上的一致性写进 unverified.txt。
- 不新增日志、环境变量或公共 API。

hosted 的边界：runner 没有 /dev/dri，llvmpipe 的软件设备没有 render node（研究 A6），真实插件路径上解析必然返回「无」。所以参数传递与 fd 生命周期由 fake libmpv 的原生测试证明（注入一个 fd），解析助手的匹配逻辑用指向 `/dev/null` 的符号链接在临时目录里证明（无需 root）；真实插件测试只证明「解析返回无时安全回落、不崩溃」。

Purpose: SC3 的宿主侧；与 16-03 一起使 GL 与 Vulkan gpu-next 都能在有硬件时加载 vaapi interop。
Output: drm_render_node.h、两个后端的接线、原生测试、unverified.txt。
