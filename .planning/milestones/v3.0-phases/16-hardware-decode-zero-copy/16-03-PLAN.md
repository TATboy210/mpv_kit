<objective>
HWD-03 的 mpv 侧与构建侧：让 Vulkan gpu-next 路径也能把宿主传入的 DRM render node 交给 vaapi，并让 hosted 的验证层 libmpv 真正编入 vaapi。

研究 3.2 的关键缺口：vo_gpu（GL 与 Vulkan 的 `gpu` 渲染器）经 `libmpv_gpu.c` 在加载 hwdec 之前把每个 native resource 注册到 ra 上；补丁 0004 的 gpu-next libmpv 后端自己调用 `fns->init` 后直接 `preinit(vo)`，而 preinit 以 libmpv 的 load_all 加载全部 hwdec——此时 ra 上没有 `drm_params_v2`，`hwdec_vaapi.c` 的 `create_drm_va_display` 取到 NULL，vaapi 必然失败。修法是在 0004 的 `libmpv_init` 中、`preinit` 之前注册它（约 15 行）。只注册 `drm_params_v2`：mpv_kit 构建关闭 x11/wayland（build.sh），`drm_draw_surface_size` 只服务 drmprime overlay（宿主传 `fd=-1`，overlay 本就会被跳过）。改动只落在 vo_gpu_next.c：libmpv_gpu.c 同时被 0001 与 0010 修改，碰它会移动 0010 的上下文，破坏「0010 与上游 ABI 逐字节一致」。

hosted 证明的边界（研究 Pitfall 4）：vaapi 的 `init` 先做 dma-buf interop 检查再建 VADisplay，hosted 的 llvmpipe/lavapipe 是否支持 dma-buf 导入不确定（A1），而且 runner 没有 /dev/dri，所以「vaapi interop 已加载」在 hosted 上不能作门禁。本计划用可判定的事实证明接线：gpu-next 下 mpv 自己的日志说明 native resource 已注册；GL 与 gpu 路径下上下文照常创建、像素正确；vaapi 的实际日志结论只记录。宿主侧 render node 的解析与传参在 16-04。

构建侧：验证层 linux 显式编入 vaapi（发布层 build.sh 已有 `-Dvaapi=enabled -Ddrm=enabled`）并断言 config.h；build.sh 增加必需特性断言，Windows 增加 D3D_HWACCEL（HWD-02 的 d3d11va 依赖它），发布层的结果由 16-06 的那一次 release dispatch 证明（不额外 dispatch）。

补丁 0004 是下游补丁，本计划可整体 revert；按 Phase 14-06 的中间树方法重生成，provenance gate 必须保持 `PATCH-DRIFT OK`。

Purpose: SC3 的 mpv 侧前提；HWD-02 的构建前提（d3d11va 编入）。
Output: 重生成的 0004 与 vendored vo_gpu_next.c、两个 smoke 的 `--drm` 变体、验证层 vaapi、build.sh 必需特性。
</objective>
