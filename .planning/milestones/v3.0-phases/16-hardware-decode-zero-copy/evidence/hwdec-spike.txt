linux (api=opengl, llvmpipe): the default list ended in software decoding for all three samples (hwdec-current=no from first frame to end, no change while playing); first frame 35-58 ms.
windows (api=d3d11, Microsoft Basic Render Driver / WARP): the default list ended in software decoding for all three samples (hwdecSeen=no); hwdec-current is sampled once a second, so whether a d3d11va entry was tried and dropped before the first frame is not visible in these lines (no verbose decoder log on this leg); first frame 62-95 ms for the default list vs 60-118 ms for hwdec=no; d3d11vaZeroCopy=false on every line.
macos (api=vulkan via MoltenVK, Apple Paravirtual device, corrected probe): the default list selected videotoolbox on h264-8bit: outcome=zero-copy, hwdecCurrent=videotoolbox, hwdecInterop=videotoolbox,vulkan, pixelformat=videotoolbox, hwPixelformat=nv12, screenshot match (diff 1.3242), flutterFrame match. The mpv log of that run shows vulkan tried first (Hardware decoding of this stream is unsupported), d3d11va-copy "Unsupported hwdec", then h264-videotoolbox used via auto-safe. requestedHwdec on the default row is vulkan,d3d11va-copy,auto-safe, the same three entries as the ROUTE-IDENTITY defaultHwdec list read at session creation; no bracketed hwdec value appears in the log ("Unsupported hwdec: [" count 0). The Phase 13 "default list chose software" reading came from feeding List.toString() back as the option and is not a product fact. hevc-8bit/hevc-10bit were measured with hwdec=videotoolbox only (gated lines), not with the default list.
hw pixelformat strings seen: videotoolbox/nv12 and videotoolbox/p010 (macOS, gated rows). d3d11, vulkan and drm_prime hardware format names (assumption A2) could not be observed on any hosted runner.
