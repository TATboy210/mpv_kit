## Summary

The release pipeline already does everything the phase needs. `release.yml` builds six LGPL bundles from pinned sources, audits and smoke-tests the packaged copies, and publishes a GitHub Release only for a `v*` tag push. A `workflow_dispatch` on the branch builds and uploads artifacts but its `publish` job is skipped. The last green dispatch (run 40907471707, sha 8310775) was built from inputs that are byte-for-byte the same as HEAD for every file that goes into a bundle, so no rehearsal build is needed unless the plan edits `release.yml`, `native/build`, `native/patches` or `tools/rea_abi_audit`. A tag run takes about 15 to 25 minutes (Windows is the critical path). I downloaded the Windows x64, Linux x64 and macOS arm64 artifacts of that dispatch and checked them: manifests verify, `pe_audit.py --forbid-gpl --forbid-angle` passes for the Windows DLLs I audited, the Windows libmpv carries 105 D3D11 string hits against 21 in dev.3, the Linux libmpv carries `libEGL.so.1` (dev.3 has none), and no macOS dylib contains a Homebrew path.

Six findings change the plan compared with the brief:

1. **Package versions and CHANGELOGs are already at `0.1.0-dev.4`** (commit 67cfb68, 2026-10-25), so the tag name matches the lockstep versions and no version bump is needed. Only the CHANGELOG text must be updated: `packages/mpv_kit_libs/CHANGELOG.md` still says the bundle "is still the 0.1.0-dev.3 release", and the `mpv_kit_video` dev.4 entry does not mention the D3D11/OpenGL backends.
2. **The three packages are published on pub.dev; latest is `0.1.0-dev.3`** (published 2026-10-16T10:40Z, 11 minutes after the dev.3 release and 9 minutes after its pin commit). A re-pin in git only reaches pub consumers when `0.1.0-dev.4` is published to pub.dev. That is irreversible (pub versions can only be retracted) and it is not in the ROADMAP success criteria. It needs its own decision (Open Question 1).
3. **The Windows leg of `flutter-plugin.yml` is not a real pinned-bundle gate today.** The log of the latest run (41065294826, job 124094812213) shows `Failed to load ...controller_channel_test.dart: libmpv is required by CI (MPV_KIT_REQUIRE_LIBMPV) but could not be loaded` and `7 tests passed, 1 failed`, yet the job is green. The Locate step exports an MSYS-style `MPV_KIT_LIBMPV_PATH=/d/a/...` that Windows Dart cannot open, and the failing native `flutter test` is swallowed because the step has no `shell:` (inferred: pwsh default). Same pattern in runs 40949963646 and 40984192897. New Windows steps must not inherit that variable.
4. **`rtx_run.sh` cannot be reused in place.** It writes to the Phase 17 `evidence/` directory and its gate compares `packages example/lib example/integration_test native` with the sha in `rtx-prep.txt`; the pin commit edits `packages/mpv_kit_libs/lib/src/bundles.dart`, so `native_equal=no` would fail the gate. Copy it into the 17.1 `tools/` directory (its paths derive from its own location). Also: `example/build/windows/x64/runner/Debug/libmpv-2.dll` currently is the Phase 17 artifact libmpv (sha256 `e63ccc2a...`), so a "pinned only" RTX run must prove the DLL it loads is the dev.4 one.
5. **PR #1 (`feat/mpv-master-upgrade` to `main`) is open**, so every push of the branch automatically runs native-verify, flutter-plugin and macos-route through the `pull_request` trigger. Branch pushes are the CI trigger; no dispatch is needed.
6. **The `v*` tag trigger also matches GSD milestone tags.** The local annotated tag `v2.0` (commit 4df1fd5, "closed by user decision as a simple close-out") is not on origin. `git push --tags` or `--follow-tags` would push it, start release.yml on it and publish a bogus `v2.0` release. Push exactly one ref: `refs/tags/v0.1.0-dev.4`.

**Primary recommendation:** Do prep (CHANGELOG/doc text, evidence) in a local commit, push it fast-forward and wait for green PR CI, then stop at one blocking `checkpoint:decision` (go/no-go for tag + push + public release, name fixed), push only `refs/tags/v0.1.0-dev.4`, let release.yml publish, then run `pin_bundles.dart v0.1.0-dev.4` and commit the pin together with pinned-only forced-`d3d11`/`opengl` steps for `flutter-plugin.yml`, wait for green PR CI, and finish with a 5-minute RTX forced-d3d11 probe against the pinned bundle using a copied `rtx_run.sh`. Keep the hook stale-stamp fix and the pub.dev publication out of the critical path.

### The stale-stamp defect (`hook/build.dart:76`) - assess
```
76:  if (stamp.existsSync() && stamp.readAsStringSync() == pinned) {
77:    return sharedLibrariesIn(extracted);
```
When the stamp matches the pin, the hook returns whatever is in `extracted/lib` without checking the directory exists. If the extracted directory was removed and the stamp survived, `sharedLibrariesIn` returns `const []` (`bundle.dart:84-91`), the hook emits no code asset, and mpv_kit silently falls back to the system libmpv or fails to find one. It was observed on this host: `docs/perf/fallback-uhd-regression.md:222` records that "the local `v0.1.0-dev.3` lib directory was empty for this reason". Today's `.dart_tool` on this host still shows `v0.1.0-dev.3/` content under the stamp scheme.

Assessment for this phase:
- A re-pin changes `bundleTag`, so `v0.1.0-dev.4/` starts empty: no stale stamp can exist for it on any machine until someone later deletes only the extracted directory. The defect does **not** block the release, the pin, the CI steps or the RTX check.
- It matters for evidence quality, not correctness of the release: a stale stamp turns "pinned bundle only" into "whatever libmpv the process found". CI is fresh every run and the Locate step already fails with `no hook bundle found` when empty (`flutter-plugin.yml:75-76`). For the RTX run the plan must assert the loaded DLL's sha256 (below).
- Fix size if done: about three lines in `build.dart` (treat the stamp as valid only when `sharedLibrariesIn(extracted)` is non-empty, else fall through to the existing `installBundle` path, which reuses a verified archive), plus moving that predicate into `bundle.dart` so `bundle_test.dart` (16 tests, no stamp test today) can cover it. It touches shipped package source and the API is untouched, but it widens the diff of the release-adjacent commits.
- **Recommendation: do not fix it in 17.1's critical path.** Keep it as the separate audit tech-debt item 3 (a quick task after the pin), unless the user opts in; if opted in, make it its own plan, after the pin plan, with a unit test written first. Whether it ships before or after the tag is irrelevant to the bundle (the hook is not inside the bundle).

### Anti-Patterns to Avoid
- **`git push --tags` / `--follow-tags` / `--mirror`:** would push local `v2.0` and `pre-261029-rcc`; `v2.0` matches `v*` and would publish a bogus release. Push `refs/tags/v0.1.0-dev.4` only.
- **Pinning from a dispatch artifact:** every build differs byte-wise; only the tag run's `SHA256SUMS` is valid.
- **Re-tagging after publication:** a moved or re-created `v0.1.0-dev.4` yields different hashes and breaks every pin made from the first one. If anything is wrong after publish, the next name is a user decision.
- **Running the RTX check with a user define or `MPV_KIT_LIBMPV_PATH`:** that is the Phase 17 artifact, not the pinned bundle.

## Common Pitfalls

### Pitfall 1: A "pinned" run that loaded the wrong libmpv
**What goes wrong:** exe dir DLLs from an earlier artifact run, a leftover `MPV_KIT_LIBMPV_PATH`, or a stale stamp make the forced-d3d11 result meaningless.
**How to avoid:** assert (1) no `hooks:` in `pubspec.yaml` (`git diff --quiet -- pubspec.yaml example/pubspec.yaml`), (2) `MPV_KIT_LIBMPV_PATH` unset, (3) the hook cache `v0.1.0-dev.4/windows-x64.ok` content equals the pinned sha, (4) sha256 of the cache's `windows-x64/lib/libmpv-2.dll` equals the exe-dir DLL and equals the entry in the downloaded tar's `MANIFEST.txt`.
**Warning signs:** `reason` shows `d3d11 (gpu-next)` but the exe-dir hash is `e63ccc2a...`.

### Pitfall 2: Pushing local tags
**What goes wrong:** see Anti-Patterns. **How to avoid:** `git push origin refs/tags/v0.1.0-dev.4` only, and print `git ls-remote --tags origin` before and after.

### Pitfall 3: Windows CI step inherits a broken libmpv path
**What goes wrong:** the Locate step's `/d/a/...` value breaks any Windows Dart process (the existing job's hidden failure). **How to avoid:** override with an empty value in the new step, and verify the load with the `cmp` identity check.

### Pitfall 4: macos-route pixel parity compares different bundles
After the pin, the HEAD leg downloads dev.4 while the pre-Phase-12 worktree (`3a5f450`) still pins dev.3 [VERIFIED: `git show 3a5f450:packages/mpv_kit_libs/lib/src/bundles.dart` -> `const bundleTag = 'v0.1.0-dev.3';`]. `check_route_probe.py` documents "same libmpv" and its tolerances (`PARITY_MAX_NONBLACK_DELTA = 0.02`, `PARITY_MAX_MEAN_DELTA = 4.0`) "must not be adjusted after seeing a result". If macos-route turns red on parity, do not change tolerances; the clean fix is to make the pre12 leg use the same pin (copy HEAD's `bundles.dart` into the worktree before `flutter pub get`). Either option is a user decision on record. dev.3 must stay published for the unchanged pre12 leg.

### Pitfall 5: Disk gate on the RTX host
`df -Pm` shows 5721 MiB free on D:, the gate needs 5632 (`MIN_DISK_MIB=5632`, `rtx_run.sh`). The 89 MiB margin can vanish with the dev.4 cache (about 21 MB tar + 50 MB extracted) and a rebuilt example (`example/build` is 615 MB now). Check the gate first; never delete anything without the user's say.

### Pitfall 6: Release failure and reruns
Past tag runs were clean; failures in earlier dispatches were real defects fixed since. A flake on an unchanged input is rerun with `gh run rerun <id> --failed` (at most once per gate, after reading logs, per the carried-over rule). The publish job only starts when all three build jobs are green, so a failed build leaves no release. If the failure is a code defect, stop: the tag can still be deleted from origin (no release exists yet) but the new tag name is the user's call.

## Risks

1. **Public release cannot be fully withdrawn.** `gh release create` publishes immediately (not draft), becomes "Latest", and assets get downloaded (dev.3 assets show 116-491 downloads). Reversible only up to the moment `publish` succeeds: before that, delete the remote tag (`git push origin :refs/tags/v0.1.0-dev.4`) and cancel the run; after that, `gh release delete v0.1.0-dev.4 --cleanup-tag` removes the page but not copies, and re-creating the same tag name would produce different hashes. Blast radius of the release alone is small (consumers only change when a pin commit reaches them: `main` and pub.dev both still say dev.3).
2. **Tags forbidden by Phase 17 authorization** (`push-authorization.txt`: `push_authorized=yes scope=push-green-only ... release_dispatch=yes`; `17-01-PLAN.md:83`: "不推其他分支或 tag"; `.continue-here.md`: "no tags"). The plan needs a fresh blocking `checkpoint:decision` before `git push origin refs/tags/v0.1.0-dev.4`, and should record the user's reply in a `push-authorization.txt` of its own, as 17-01 did.
3. **Release-build failure and reruns:** history above; one `gh run rerun --failed` per gate for infra only, poll at least 120 s. Never move or re-push the tag.
4. **macOS bundle changes under `macos-route` and native-verify macOS legs.** `MACOS-DYLD ... homebrew=0` is produced by `tools/macos_dyld_images.dart` against the **staged branch build** (`native-verify.yml:310-311`), not against the release bundle, so the re-pin cannot change that line. What changes: macos-route (see Pitfall 4) and the macOS cells that load the pinned dylibs. I checked the candidate macOS bundle statically (no Homebrew paths; `@loader_path` closure from `dylibbundler`; MoltenVK inside); a dynamic `MACOS-DYLD`-style check on the release bundle does not exist and would need the macOS runner.
5. **LGPL/GPL audit:** green for the candidate on the Windows DLLs I ran, and the same audits run in `package.sh` for every Windows bundle during the tag run; Linux/macOS rely on `check_gpl` name matching and `require_prefix_avcodec`. Nothing in the diff versus dev.3 adds GPL; additions are shaderc/SPIRV-Cross (permissive) on Windows.
6. **Bundle size:** Windows +4 MB compressed (+28 percent unpacked), other targets about equal. Hook download time and `flutter build` output grow accordingly.
7. **Behavior change for existing users after a consumer upgrades to a dev.4 pin** (auto chains, README `:172-190`):
   - Windows: `vulkan/gpu-next, d3d11/gpu-next, vulkan/gpu, d3d11/gpu, software`. With a working Vulkan 1.3 device nothing changes. Where `vulkan/gpu-next` fails but `vulkan/gpu` would have worked, the second candidate is now `d3d11/gpu-next` instead of `vulkan/gpu` (dev.3 could not create D3D11). Where Vulkan is unusable the app lands on D3D11 instead of software, which is the intent. D3D11 on the GTX 960M dropped more frames than Vulkan (D3D-08 decision), so some laptops get D3D11 rather than software, a better outcome than software.
   - Linux: `vulkan/gpu-next, opengl/gpu, vulkan/gpu, software`. With a working Vulkan 1.3 nothing changes. Hosts where `vulkan/gpu-next` fails now try OpenGL before `vulkan/gpu`; every GL result so far is Mesa llvmpipe, real NVIDIA/AMD/Intel GL, Wayland EGL, real X11 and GL device loss are unverified (audit tech debt, Phase 15 `unverified.txt`). `libmpv.so.2` now links host `libEGL.so.1` (A2).
   - macOS: no chain change; dev.4 macOS bundle differs in build inputs only.
8. **Nothing in tests or goldens asserts the bundle tag or hashes.** Searched `packages/*/test`, `example/integration_test`, `tools`: only `tools/pin_bundles.dart` and `native-verify.yml:123` (the live `--check`) read `bundles.dart`; `packages/mpv_kit_libs/lib/mpv_kit_libs.dart` re-exports `bundleTag` (a constant, not a signature change).
