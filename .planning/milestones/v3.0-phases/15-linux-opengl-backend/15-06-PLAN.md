<objective>
GLX-04 的行为证明与 15-03 发现的探测缺陷修复。

1. **Vulkan 不可用时自动落到 GL（SC4）。** 托管 ubuntu runner 上 lavapipe 可用，auto 总是选 Vulkan；要证明「Vulkan 不可用 → opengl/gpu 获胜并在 reason 中写明原因」，CI 用 Vulkan loader 的环境变量让 ICD 清单不存在（实例创建失败，与 windows-2025 runner 上的 `vkCreateInstance failed` 同一形态），在真实插件上看 auto 的结果。
2. **探针缺陷（15-03 的 D-THREAD）。** 进程中第二个及之后的控制器在平台线程上建不出探测 context，Phase 12 起一直悄悄落到软件渲染（15-05 接链之后则落到 OpenGL）。按 15-03 的结论（`IMPLICATION=helper-thread`）把探测移到一个新线程上执行——与 OpenGLBackend 的 create 期线程同一原则，与平台线程上 Flutter/GDK 的 context 状态无关。显示句柄仍在平台线程上经 GDK 取得（GDK 只能在平台线程上用）。这是一个现有缺陷的修复，所以先有失败的断言：`SECOND-CONTROLLER` 断言在修复前（15-05 的状态）对默认运行必然失败——该红色只在本地推理与 15-05 的 CI 日志中可见，不单独推送红色提交（push-green-only）：断言与修复在同一个提交里。

**15-05 CI 日志即修复前证据：** 15-05 的默认运行中 soak 循环控制器的 reason 是 `opengl (gpu) on …; vulkan/gpu-next unavailable: platform interop unavailable: …` 一类（Vulkan 被探测失败排除）；本计划修复后它们应全部为 vulkan。把 15-05 的那组计数作为修复前数据写进 SUMMARY。

Output: Vulkan 不可用的 CI 运行、线程无关的探测、第二个控制器的一致性断言。
</objective>
