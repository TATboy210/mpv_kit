# 8K Memory — Root-Cause Verification and `vd-lavc-threads` Cap (dev.6)

**Date:** 2026-11-02 · **Code state:** dev.5 tree + the dev.6 candidate
(`player.dart`: 8K software-decode thread cap) · **libmpv:** dev.5 pinned bundle
(`v0.1.0-dev.5`, windows-x64) · **Machine:** Windows 11 x64, NVIDIA RTX 4060 Laptop
(8188 MiB), 16-thread CPU, **32 GiB RAM**, 1 GiB pagefile.

**Samples** (test-only, never shipped):

- `D:/media/dvb_8k_pq10.ts` — DVB 8K HEVC Main10 50 fps, 7680×4320, 30 s, 37.5 MB,
  CC BY 4.0 (up-converted from 4K by DVB; real HEVC encode, real decode path).
- `D:/media/sample8k_hevc10.mkv` — lavfi `testsrc2` 7680×4320 50 fps encoded to
  HEVC Main10 by the local FFmpeg build, 10 s, 105 MB (synthetic content, used only
  to cross-check that the numbers are source-independent).

## Pre-registered rules

Measured before any product change:

1. A candidate is **confirmed** when (a) baseline peak memory at 8K is high enough to
   threaten a 16 GiB machine's commit limit, and (b) removing the factor (or reducing
   it) in an A/B run lowers peak RSS by ≥1 GiB, or eliminates the growth.
2. Local-file playback must show the demuxer cache staying small; if it does, demuxer
   timing options are **not-confirmed** for this scenario regardless of theory.
3. Any option that changes GPU memory must show a measurable change in `nvidia-smi`
   `memory.used`; otherwise it is **not-confirmed** for the zero-copy path.
4. Unmeasurable items are recorded as **not-confirmed (not measured)**, never inferred.

## Method

- **Headless decode/demux memory** — one-off probe (`.planning/tmp/probe_8k.dart`,
  not product code): `Player` with `vo=null`, `ao=null`, `loop-file=inf`, 30 s per
  variant, peak `ProcessInfo.currentRss`. This isolates demuxer + decoder memory.
- **Real plugin path** — `example/integration_test/uhd_endurance_test.dart` with
  `MPV_KIT_BENCH_SOURCE` (real file), `MPV_KIT_BENCH_RENDER=1` (real texture at
  7680×4320, i.e. the largest possible ring), unmodified test code. VRAM sampled
  externally with `nvidia-smi` every 5 s.
- Hardware decode on this GPU is Vulkan Video zero-copy
  (`hwdecCurrent=vulkan`, `pixelformat=vulkan`, `hwPixelformat=p010`).

## Results

### A. Headless memory by configuration (peak RSS, 30 s, DVB sample)

| Variant | Peak RSS | Note |
|---|---:|---|
| default (`hwdec` list, `vo=null` → `d3d11va-copy`) | 1167 MiB | copy-back path |
| `hwdec=no` (mpv auto = 16 threads) | **3533 MiB** | software decode |
| `hwdec=no`, `vd-lavc-threads=8` | **2221 MiB** | software decode |
| `hwdec=no`, `vd-lavc-threads=4` | 1609 MiB | software decode |
| `hwdec=d3d11va-copy`, `hwdec-extra-frames=1` | 1167 MiB | **no change vs 6** |
| `hwdec=vulkan` (no custom VO interop → software) | 3533 MiB | same as software |
| `demuxer-max-bytes=64MiB` | 1167 MiB | **no change** |
| `cache=no` | 1143 MiB | no change |

The synthetic 105 MB clip reproduces the same ordering (1409 / 3688 / 2295 / 1710 MiB),
so the result is source-independent.

**Demuxer cache stayed below ~25 MiB** in every local-file run (`demuxer-cache-state`
`fw-bytes`), far under the 256 MiB 8K budget: the UHD-01 budget is not the driver for
local 8K files, and applying it earlier (`on_preloaded`) would not change this case.

### B. Software-decode thread matrix (8K, 20 s, speed=4)

`time-pos` advance per 20 s wall clock measures achievable decode progress; peak RSS
is the same run.

| Threads | Peak RSS | Position in 20 s | Δ RSS vs 16 | Δ throughput |
|---:|---:|---:|---:|---:|
| 16 (mpv auto) | 3433 MiB | 20.56 s | — | — |
| 14 | 3254 MiB | 20.34 s | −179 MiB | −1.1% |
| 12 | 2908 MiB | 20.06 s | −525 MiB | −2.4% |
| 10 | 2700 MiB | 19.68 s | −733 MiB | −4.3% |
| **8 (dev.6 cap)** | **2213 MiB** | **18.94 s** | **−1220 MiB** | **−7.9%** |

At 8K the decode is memory-bandwidth bound: 12→16 threads buys ~2% throughput for
525 MiB of RSS, and the fixed 16-thread auto never exceeded ~1× realtime on this
machine. Capping at 8 saves 1.2 GiB for ~8% throughput — 8K software decode was
already at/below realtime at 16 threads on this CPU.

### C. Real plugin path (Vulkan zero-copy, 7680×4320 texture)

| Run | Duration | RSS (end) | VRAM (peak) | Gates |
|---|---:|---:|---:|---|
| dev.5, 8K real file | 180 s | 892 MB | 3.65–4.00 GB | all green, 0 drops |
| dev.5 + `hwdec-extra-frames=2` (A/B) | 80 s | — | 4.03 GB | **identical VRAM** |
| dev.6 candidate (8K cap) | 1800 s | **889 MB** | 3.76 - 4.00 GB | **all green, 0 drops** |

The 30-minute run (`8k-real-dev6-30min`, label in `uhd_8k_30min.log`) finished with
`frameDropCountFinal=0`, `decoderFrameDropCountFinal=0`, `renderErrors=0`,
`deviceLost=false`, `|total-avsync-change|` 0.02 s and ~50 fps estimated. Mid-run
sampling showed working set 826–849 MB and private commit 2.7–3.0 GB (the private
figure includes the Vulkan driver allocations behind `nvidia-smi`'s 3.8 GB).

`hwdec-extra-frames` has **no effect** on the Vulkan Video pool (dynamic surface
allocation), so lowering it at 8K is not a memory lever for the shipping default path.

## Verdict per candidate

| # | Candidate | Verdict | Evidence |
|---|---|---|---|
| C1 | Software-decode frame threads (`vd-lavc-threads=0` → 16 at 8K) | **confirmed** | −1.22 GiB at 8 threads; 16 threads is the only configuration that puts a single decode path above 3 GiB at 8K |
| C2 | `hwdec-extra-frames=6` at 8K | **not-confirmed** | no RSS change in copy mode, no VRAM change in zero-copy mode |
| C3 | Demuxer budget applied only at first `videoParams` | **not-confirmed (local files)** | cache stayed <25 MiB; budget of 256 MiB never approached. Not implemented (no measurable benefit) |
| C4 | Render ring at 8K texture (8 × BGRA8) | **not a factor in normal windows** | real window sizes request widget×dpr; the 180 s run at an artificial 8K texture still peaked at 892 MB RSS because decode is zero-copy |
| C5 | Software-renderer `retired_`/`older_` generations | not measured | out of scope (Dart-only change policy); noted in `CONCERNS.md` |
| C6 | `demuxer-donate-buffer` accounting | **not-confirmed** | donation only at EOF and capped by fwd+back (`options.rst`); local cache far below budget |

## Change

`Player.decoderThreadsForTesting` no longer returns `0` (mpv auto = 16) above
4096×2304; the 8-thread cap that already applied to 4K now applies to 8K and above.
The hook that applies it (`on_preloaded`), the user-override rules and every value
at ≤4K are unchanged.

## Residual unknowns

- Linux/macOS: not measured (no real hardware here).
- 8K AV1 software decode: not measured (no AV1 8K sample); the memory model is the
  same frame-threading multiplier.
- 30-minute 8K result: completed on the hardware zero-copy path (see `C`).
- Software-decode plateau with the dev.6 cap (10 minutes, `hwdec=no`, same real
  file): `vd-lavc-threads=8` was applied, peak RSS 2314 MiB, flat at
  2296 MiB from minute 2 to minute 10 — a plateau, not growth.
